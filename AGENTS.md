# Repository engineering guidelines

## Documentation and review

- Write documentation, comments, issues, pull requests, release notes, and new commit messages in a concise engineering voice. Explain the concrete change, decisions, validation, and limitations with consistent project terminology.
- Omit development-tool attribution, assistant-to-user conversation, prompt transcripts, and task-completion or handoff narration from project documentation. Keep private working notes outside the repository.
- Preserve contributor identities, required notices, truthful history, provider and dependency identifiers, API references, and necessary technical fixtures. Never invent authorship, test results, experience, or release readiness.
- Before publishing, review the complete proposed text in context for conversational narration, unnecessary attribution, repetitive wording, unsupported claims, and private workflow details. Keyword checks supplement contextual review.
- Use focused working branches and descriptive PR titles. Preserve application behavior, other contributors' statements, and shared Git history. Check deployment triggers before pushing; leave deployment-sensitive documentation changes pending when publication would deploy the application.
